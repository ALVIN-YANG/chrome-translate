# 开源发展路线

目标是让用户愿意长期使用、遇到问题能复现、贡献者能独立改进。功能列表、文档数量和单次测试通过都不能证明项目已经成为顶级开源项目。

## 当前基础

已有独立文本、划词三入口、网页双语、自定义模型与声音，以及真实 MiniMax 和微软验证记录。当前公开仓库仍处早期，不能推断已有稳定用户、社区贡献或跨平台安装验收。

## 下一阶段

| 优先级 | 方向 | 验收依据 |
| --- | --- | --- |
| P0 | 明确开源许可（已选择 MIT） | 根目录许可证、包元数据和发布包一致 |
| P0 | 可复现的安装与发布 | 贡献者从干净检出执行检查与打包；公开包摘要吻合；记录真实首次安装反馈 |
| P0 | 把回归留在 CI | 无真实 Key 的 Node 与 Chromium 检查持续执行；失败能定位到截图、trace 或请求契约 |
| P1 | 可理解的数据边界 | 权限与文本去向有源码依据；漏洞可私密报告；配置不进入截图、日志和发布包 |
| P1 | 真实采用反馈 | 从实际用户收集安装成功率、常用场景、失败原因和再次使用反馈；不加入未获同意的遥测 |
| P1 | 社区可独立贡献 | 问题模板提供足够复现信息；贡献者无需维护者机器或真实账号即可验证 PR |
| P2 | 国际用户可用 | 英文安装/开发文档与实际界面边界一致；再根据真实需求推进界面本地化 |
| P2 | 兼容性与性能 | 用公开、可复现的站点样本验证长文、动态内容、特殊布局、取消和大页面资源占用 |

先修复影响使用的缺陷，再增加功能。PDF、图片、字幕、子框架和 Shadow DOM 不应因为竞品具备就盲目加入；需要先有真实需求、权限/数据方案与可验证的支持边界。

## 如何判断有进展

每次发布记录：完成了哪个用户任务、什么检查证明它可用、还有哪些限制，以及公开反馈带来了什么改变。Star、下载量和贡献数可作为观察指标，不替代用户是否完成任务，也不虚构增长。

对外发布、邀请评测和社区交流需维护者选择对象和授权；不自动群发推广、制造评价或提交无关 Issue。
